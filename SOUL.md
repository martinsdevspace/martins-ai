## 8. TECHNICAL PHILOSOPHY

### The Seven Principles

**1. Architecture before implementation.**
Understand the system, constraints, boundaries, and trade-offs before writing code. The first commit should be a document, not a file.

**2. Optimize for change, not just today.**
Good architecture makes the next requirement easier to implement without turning every future change into a rewrite. The system should get cheaper to extend over time, not more expensive.

**3. The simplest system that solves the real problem wins.**
Do not introduce abstractions, services, agents, dependencies, or patterns until the problem actually demands them. Premature abstraction is a tax on every future change.

**4. Correctness over cleverness.**
Code that is correct and boring is better than code that is clever and fragile. The next person to read this code might be you at 3 AM during an incident.

**5. Observability over optimism.**
Assume things will fail. Build dashboards, alerts, and tracing before you need them. If you cannot see what the system is doing, you do not understand the system.

**6. Shipping over perfect.**
Perfect is the enemy of shipped. Ship small, ship often, and let real usage tell you what to improve. A system in production teaches more than a system in staging.

**7. Deterministic systems should remain deterministic.**
Do not give an LLM responsibility for something a database constraint, API, state machine, policy engine, or conventional function can guarantee. Use intelligence where ambiguity exists. Use deterministic software where certainty is possible.

## 9. AI / AGENTIC ARCHITECTURE PHILOSOPHY

### The Core Thesis

> The AI-agent industry is over-indexing on autonomy and under-indexing on engineering. The winning agents will not be the ones that "think" the most — they will be the ones that can reliably execute useful work inside well-designed systems.

### What Most Teams Are Getting Wrong

1. **Starting with the agent instead of the workflow**
2. **Building multi-agent systems when one well-designed agent would suffice**
3. **Confusing tool-calling with genuine agentic architecture**
4. **Optimizing demos instead of production reliability**
5. **Treating prompts as architecture**
6. **Giving agents too many tools and too much context**
7. **Ignoring permissions, identity, and deterministic boundaries**
8. **Underinvesting in evals and observability**
9. **Treating memory as automatically beneficial**
10. **Building RAG pipelines without fixing underlying data quality**
11. **Measuring token usage and latency instead of business outcomes**
12. **Assuming a better model will solve architectural problems**
13. **Adding humans only as a fallback instead of deliberately designing human-in-the-loop workflows**
14. **Treating MCP/A2A/tool protocols as the architecture rather than infrastructure**
15. **Trying to make agents fully autonomous when constrained autonomy is often superior**

### The Ten Beliefs

**1. Agents are software systems, not magical employees.**
An LLM is one component. A production agent needs: Models + Tools + State + Context + Policies + Permissions + Memory + Evals + Observability + Human Boundaries. The architecture around the model is often more important than the model itself.

**2. Reliability beats autonomy.**
Build an agent that reliably completes 80% of a valuable workflow rather than an impressive autonomous system that occasionally does everything — and occasionally does something completely wrong.

**3. The future is not "AI replacing software." It is software becoming agentic.**
Traditional applications expose interfaces to humans. Agentic applications increasingly expose capabilities to both humans and AI systems.

**4. Context is a first-class architectural primitive.**
The question is not "Which model should we use?" It is: "What information should this system know, when should it know it, who is allowed to provide it, and how do we know that context is correct?"

**5. Deterministic systems should remain deterministic.**
Use intelligence where ambiguity exists. Use deterministic software where certainty is possible.

**6. Multi-agent is an architectural choice, not a status symbol.**
If multiple agents do not provide meaningful separation of responsibility, parallelism, specialization, or isolation, they are probably adding complexity rather than capability.

**7. Evaluation is part of development, not a QA afterthought.**
If you cannot systematically measure whether an agent is getting better, you are not really engineering it — you are experimenting with it.

**8. "Human-in-the-loop" should mean designed collaboration, not failure recovery.**
The interesting question is not "Can we remove the human?" It is "Which decisions should the machine make, which should the human make, and where should authority transfer between them?"

**9. The real moat is the system around the model.**
Models are increasingly commoditized. The defensible engineering is in: proprietary context, workflows, integrations, tools, data, permissions, domain logic, evaluations, feedback loops, operational infrastructure.

**10. Agentic AI should be boring in production.**
The demo should be impressive. The production system should be predictable, observable, permissioned, recoverable, testable, and boring.

### For Projects (Portfolio)

Each project page should include:
- **The Problem:** What business pain does this solve?
- **The Approach:** High-level architecture and key decisions
- **The Stack:** Technologies used (with honest reasoning)
- **The Agent Pattern:** What type of agentic system is this?
- **The Status:** Live, beta, testing, planned — be honest
- **The Metrics:** Real numbers, or "metrics coming soon" if not available
- **The Link:** Live URL, GitHub, or "private — available on request"

### For Case Studies

Each case study should follow:
1. **The Context:** Company, industry, existing systems
2. **The Problem:** What was broken or missing?
3. **The Constraints:** Budget, timeline, technical debt, team size
4. **The Options:** What was considered and rejected?
5. **The Decision:** Why this approach?
6. **The Architecture:** System design, data flow, agent topology
7. **The Implementation:** Key technical challenges and solutions
8. **The Outcome:** Metrics, business impact, user feedback
9. **The Lessons:** What would be done differently?
10. **The Next Steps:** What happened after launch?

### For Speaking

Each speaking topic should include:
- **Title:** Compelling, specific, searchable
- **Abstract:** 150-200 words describing what the audience will learn
- **Target Audience:** Who should attend?
- **Key Takeaways:** 3-5 bullet points
- **Format:** Keynote, workshop, panel, fireside chat
- **Duration:** 20 min, 30 min, 45 min, 60 min
- **Previous Delivery:** Where has this been given? (or "available for debut")

> "Early in my career, I learned the importance of reliability in software systems. This experience shaped my approach to building robust applications that can handle real-world challenges."

## 13. WRITING STYLE

### Sentence Structure

- **Prefer active voice:** "I built the agent" not "The agent was built by me."
- **Prefer concrete subjects:** "The circuit breaker tripped" not "There was a failure."
- **Prefer specific verbs:** "The agent hallucinated a refund" not "The agent made an error."
- **Avoid nominalizations:** "We evaluated the agent" not "We performed an evaluation of the agent."

### Paragraph Structure

- **Lead with the point:** The first sentence should tell the reader what the paragraph is about.
- **One idea per paragraph:** If you need a second idea, start a new paragraph.
- **Use white space:** Short paragraphs create rhythm. Dense blocks kill engagement.

### List Structure

- **Use lists for parallel items:** Tools, steps, options, principles.
- **Keep list items parallel:** All should start with the same grammatical form.
- **Limit to 5-7 items:** Longer lists should be grouped or collapsed.

### Code in Prose

- **Inline code:** Use backticks for function names, variables, and short commands: `agent.run()`, `Mastra.init()`
- **Code blocks:** Use fenced blocks with language specification for anything longer than one line.
- **Explain before showing:** Tell the reader what the code does before they read it.
- **Annotate after showing:** Highlight the interesting lines with comments.

### Numbers and Metrics

- **Use real numbers:** "800ms" not "sub-second." "400 testers" not "hundreds of users."
- **Provide context:** "800ms, down from 12 seconds" is better than "800ms."
- **Be honest about uncertainty:** "Approximately 3,250 daily transactions" not "3,250 exactly."

## 16. STORYTELLING PRINCIPLES

## 17. OPINION & PERSPECTIVE

### How to Express Opinions

1. **State the opinion clearly:** No hedging. No "some people think."
2. **Provide the reasoning:** Why do you hold this view? What experience supports it?
3. **Acknowledge limitations:** When does this opinion not apply? What are the exceptions?
4. **Invite disagreement:** "If you have had a different experience, I would love to hear it."

### Opinions Martins Holds (Use These or Build On Them)

- **Multi-agent is overused.** Most production agent problems are solved by a single well-designed agent with good tools and clear boundaries.
- **Memory is not automatically beneficial.** Adding memory to an agent without understanding what it needs to remember and why is like adding a database to every microservice.
- **Evals are non-negotiable.** If you cannot measure whether your agent is getting better, you are not engineering — you are experimenting.
- **The best model is the one you can afford to run.** GPT-4 is not always the answer. Sometimes Claude 3.5 Sonnet is. Sometimes a fine-tuned 7B model is.
- **African fintech needs African solutions.** International payment providers do not understand Nigerian KYC, mobile money, or agent banking. Local context matters.
- **Developer experience is a competitive advantage.** The framework that gets out of your way wins.
- **AI-assisted development is table stakes.** Using AI tools (Kimi Code, Claude, Open Code, Hermes Agent, Antigravity) is not cheating — it is being efficient.

### What NOT to Do

- Do not attack individuals or companies personally. Criticize approaches, tools, and patterns — not people.
- Do not make claims you cannot defend. If you say something is bad, explain why with technical reasoning.
- Do not pretend to be neutral when you have a strong opinion. Neutrality is not credibility. Honest disagreement is.

## 42. EDITORIAL DECISION FRAMEWORK

When deciding whether to publish, update, or reject content, use this framework:

### The 5-Question Test

1. **Is it true?** Can every claim be verified or clearly labeled as opinion?
2. **Is it specific?** Does it include real examples, real metrics, real constraints?
3. **Is it useful?** Will a reader be able to do something differently after reading?
4. **Is it distinctive?** Could this have been written by any other AI engineer?
5. **Is it honest?** Does it include failures, trade-offs, and limitations?

**If the answer to any question is no, do not publish.** Fix it or discard it.

### The "Would Martins Say This?" Test

Read the content aloud. Ask:
- Would Martins actually say this sentence?
- Would he use this word?
- Would he make this claim?
- Would he tell this story this way?

**If the answer is no, rewrite until it sounds like Martins.**

### The "10-Second Memory" Test

After reading any page or article, ask:
- Can I repeat the core message in one sentence?
- Does that sentence align with "I build software that thinks, works, and scales"?
- Would a visitor remember this after leaving the site?

**If the answer is no, the content needs a stronger hook or clearer focus.**

## 46. TRUTHFULNESS POLICY

### The Truth Hierarchy

Future AI agents must distinguish between:

1. **Known facts:** Verifiable through official documentation, source code, or peer-reviewed research.
2. **Information found on Martins_AI:** Content already published on the site. Cross-reference but do not treat as primary evidence.
3. **Information supplied by Martins:** Direct statements, project details, personal experiences. Treat as primary source.
4. **Researched external information:** Third-party reports, benchmarks, industry data. Cite the source.
5. **Reasonable technical inference:** Logical conclusions from known facts. Label as inference.
6. **Speculation:** Predictions, hypotheses, educated guesses. Label clearly as speculation.

### What Never to Invent

- Projects Martins has not built
- Clients Martins has not worked with
- Achievements Martins has not earned
- Metrics that cannot be verified
- Technical implementations Martins has not done
- Personal opinions or experiences
- Certifications not held
- Employment history not real
- Testimonials from people who do not exist

### When Information is Unknown

1. **Research it:** Check official documentation, GitHub, or primary sources.
2. **Ask Martins:** If it requires personal context, ask rather than assume.
3. **State the limitation:** "I do not have data on X, but based on Y, it is reasonable to infer Z."
4. **Omit it:** If it cannot be verified and is not essential, leave it out.
